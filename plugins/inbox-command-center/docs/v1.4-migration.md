# v1.4 — Migration Sketch

The v1.3 → v1.4 upgrade is the largest update to date. It touches the connection layer (Rube → Composio), the workspace location and structure, the rule schema, and the data model for VIPs and tasks.

The migration is **skill-driven, not bash-driven** — Claude detects v1.3 state on first v1.4 launch and walks the user through the move interactively. This matches the v1.1 plugin-update-notification pattern users are already familiar with.

---

## Detection logic (runs at every triage / setup-wizard invocation)

```
SKILL preamble:
  1. Read .claude-plugin/plugin.json → current_version (e.g. "1.4.0")
  2. Resolve workspace path:
       a. Try ~/Inbox Command Center/.meta.json (v1.4 path)
       b. Try ~/Library/Mobile Documents/com~apple~CloudDocs/inbox-command-center/config.md (v1.3 iCloud)
       c. Try ./inbox-command-center/config.md (v1.3 local)
  3. If v1.4 path exists → installed_version from .meta.json → proceed normally
  4. If only v1.3 path exists → MIGRATION REQUIRED
  5. If neither exists → fresh install → run setup-wizard
```

### Stage 3 — Data file migrations

```
Step 2 of 7 — Reshaping your data files

I'll convert these in place. Each conversion shows you the before/after
so you can spot-check.

  • vip-contacts.md → contacts.md (with [VIP] tags + interaction timeline scaffolding)
  • tasks.md → todos.md + followups.md (split by item type)
  • rule-suggestions.md → rules-review-queue.md (rename only)
  • rules.md → adds Stakes: and Scope: fields per rule (auto-tagged conservatively)

[Proceed] [Show me one example first]
```

**Per-file conversion:**

#### `vip-contacts.md` → `contacts.md`

Old format (v1.3):
```markdown
## Bryan Howell
- Email: bryan@dieselpowerproducts.com
- Relationship: Client / vendor
- Always reply within: 4 hours
- Notes: Prefers concise, numbers-forward replies.
```

New format (v1.4):
```markdown
## Bryan Howell <bryan@dieselpowerproducts.com> [VIP]
**Review:** monthly | **Since:** 2026-04 (migrated from v1.3)
- Tone: Prefers concise, numbers-forward replies
- Reply target: within 4 hours
- Inboxes seen: [populated on first triage]
- Recent context: [populated by next Fireflies pull]
```

#### `tasks.md` → `todos.md` + `followups.md`

Split logic:
- Tasks where `Source = Email` AND user is **awaiting reply** → `followups.md`
- All other open tasks → `todos.md`
- Done tasks (status `✅`) → discarded (the session log will pick up new completions going forward)

Old format (v1.3):
```markdown
| ID | Created | Due | Source | From | Description | Priority | Status |
| T012 | 2026-04-15 | 2026-04-20 | Email | Joel Barbour | Confirm Q3 numbers | HIGH | ⬜ Open |
| T015 | 2026-04-18 | — | Email | Annie | Awaiting reply re budget | MED | ⬜ Open |
```

New format (v1.4):
```markdown
# todos.md
- [ ] Confirm Q3 numbers — from Joel Barbour — added 2026-04-15 — due 2026-04-20

# followups.md
- Annie — re: budget — sent 2026-04-18 — waiting 19 days
```

#### `rules.md` schema upgrade

For each existing rule, add two fields with conservative defaults:

| v1.3 action | Default `Stakes:` | Default `Scope:` |
|---|---|---|
| Categorize / mark / label | `low_stakes` | per-inbox (current default account) |
| Archive | `low_stakes` | per-inbox |
| Move to folder | `low_stakes` | per-inbox |
| Auto-junk / trash | `low_stakes` | per-inbox |
| Permanent delete | **`high_stakes`** | per-inbox |
| Auto-forward | **`high_stakes`** | per-inbox |
| Auto-reply / template send | **`high_stakes`** | per-inbox |
| Unsubscribe | `low_stakes` | per-inbox |
| VIP escalate / VIP-related | `low_stakes` | **global** (VIPs are inherently global) |

User reviews tagged rules at next rule-review cycle. They can flag rules global anytime.

#### `rule-suggestions.md` → `rules-review-queue.md`

File rename only. Content preserved verbatim. Update any references in skill code.

### Stage 4 — Composio connection migration

```
Step 3 of 7 — Connection layer: Rube → Composio

v1.4 standardizes on Composio for email and other API connections. Rube
is removed. You'll re-authenticate accounts that previously ran on Rube
or native Gmail MCP.

What you need to do:

  Native MCPs (kept — no action needed):
    ✓ Slack — already on native MCP
    ✓ Google Calendar — already on native MCP
    ✓ Fireflies — already on native MCP
    ✓ iMessage — AppleScript (no auth)

  Migrating to Composio (re-auth required):
    ⚠ Gmail (was native MCP): re-auth via Composio
    ⚠ Outlook (was Rube): re-auth via Composio
    ⚠ Otter / Gong / Fathom (were Rube): re-auth via Composio

Do you have Composio access?

  [ ] Yes — proceed to OAuth flow for each account
  [ ] No, but I'm at Strategy Labs
      → Email scott@strategylabs.us to be added to the SL team account.
        I'll wait. Type "ready" when access is confirmed.
  [ ] No, I'll set up my own Composio account
      → Walk through composio.dev signup (~3 min), then return here.
  [ ] Skip — use limited fallback (Gmail-only, single account, native MCP)
      → Warning: you'll miss Outlook, multi-account, Otter/Gong/Fathom.
```

**Skill action per account:**
1. Call `mcp__claude_ai_Composio__COMPOSIO_MANAGE_CONNECTIONS` to initiate OAuth
2. Wait via `COMPOSIO_WAIT_FOR_CONNECTIONS` until user completes browser flow
3. Verify with a test call (`GMAIL_FETCH_EMAILS` with `max_results: 1`)
4. Append to `connected_inboxes[]` in `.meta.json` with alias / platform / account address
5. After last account: confirm count + emails reachable

## Edge cases

| Scenario | Behavior |
|---|---|
| User had no v1.3 data (fresh install) | Skip migration — go straight to setup-wizard |
| v1.3 path exists but is empty / corrupt | Skip migration — go to setup-wizard, log warning |
| User has both v1.3 and partial v1.4 paths | Don't auto-merge. Prompt: "I see partial v1.4 data and a v1.3 backup. Which is canonical?" |
| Composio OAuth fails mid-migration | Save migration state to `.meta.json.migration_state`. Resume from last completed step on next launch. |
| User cancels mid-migration | Old workspace stays untouched. Partial v1.4 workspace gets removed. Show: "Migration cancelled. Your v1.3 setup is unchanged. Run /setup-wizard when ready." |
| User on second device (cross-device sync) | First device migrates. Second device sees new path on next iCloud sync; reads `.meta.json` and registers itself in `devices[]`. No second migration needed. |
| User skips Composio (fallback path) | Mark `.meta.json.fallback_mode: true`. Disable multi-account, Outlook, Otter/Gong/Fathom features. Native Gmail MCP only. Warn at every triage start about reduced functionality. |
| User's existing rules are ambiguous re stakes | Default to `high_stakes` if action could harm (delete-permanent, auto-forward, auto-reply). Default `low_stakes` for everything else. User reviews on next rule cycle. |

## Rollback procedure

If a user wants to revert to v1.3 within 30 days:

1. Quit Claude Code
2. In Finder: navigate to `~/Library/Mobile Documents/com~apple~CloudDocs/Inbox Command Center/.v1.3-backup/`
3. Move contents back to `~/Library/Mobile Documents/com~apple~CloudDocs/inbox-command-center/`
4. Reinstall plugin v1.3 from marketplace (or `git checkout v1.3.0` in the plugin repo)
5. Relaunch — v1.3 resumes with original data

After 30 days, the migration cleanup task removes `.v1.3-backup/` (with one final user-confirm prompt).

---

## What this migration does NOT do

- Does not migrate Composio account itself — user provides the account (SL team or self-signup)
- Does not auto-import Fireflies historical transcripts older than 30 days (intentional — voice signal degrades)
- Does not migrate Google Sheet / ClickUp task data (user keeps those as external systems if they want; canonical store moves to todos.md / followups.md)
- Does not modify Gmail labels or Outlook folders that already exist (synthetic ICC folders are created additively)
- Does not change cross-device sync mechanics (still iCloud Drive; just a renamed root folder)

---

## Implementation notes

- **All migration logic lives in the skill**, not in a separate command. The skill's session-start preamble checks for v1.3 state and triggers the flow inline.
- **No new bash scripts.** This is a Claude Code plugin; we use Filesystem MCP + Composio MCP tools.
- **Idempotent.** Re-running migration on a partial state is safe — each step checks if its work is already done.
- **Logged.** Every migration step appends to today's session log so users have a full audit trail.
